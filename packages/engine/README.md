# refraction-engine

Convert macOS **Liquid Glass `.icon` bundles** into small, portable,
procedural **recipes** — rendered by a shared JS engine in Node, browsers,
and edge runtimes with no canvas, no rasters, and no image decoding — and
**calibrated by RMSE** against Apple's own renderer (ictool).

Formerly the standalone `glass-to-LUT` repository; folded into this
monorepo as the research layer behind the recipe-backed bundles.

```
.icon bundle ──┬── structure (icon.json, SVG layer paths)
               │
ictool renders ┴── measurements (fills, materials, background, lighting)
                        │
                        ▼
      engine.mjs  +  recipes/<id>.mjs     →  createLiquidRenderer(recipe)
      (shared, ~26 KB)  (per icon, 4–65 KB)    .render() / .dataUri()
```

## The idea

Icon Composer's Liquid Glass rendering is a physical-ish system: a squircle
body with measured edge lighting, glass layers that refract what's beneath
them through a height field, translucent material overlays, shadows,
speculars. Most of it is *code* — and code is nearly free to ship. What
can't be derived is *measured*:

- **Material LUTs** — measured once, shipped with the engine (body-light
  field) or per icon (glass affine responses `k·bg + c`, solved with a
  two-gray instrument driven through ictool automatically).
- **Colors** — sampled from ground-truth renders, because declared
  Display-P3 fills pass through gamut mapping that colorimetric math does
  not reproduce.
- **A residual lightmap** — the final `GT − render` field, luma-only with a
  fitted white-restore chroma model, baked self-consistently against this
  renderer's own first pass.

**Everything structural comes from `icon.json`; everything perceptual is
MEASURED from ictool renders.**

## Using recipes

```js
import { createLiquidRenderer, loadRecipe } from "refraction-engine";

const r = createLiquidRenderer(await loadRecipe("spotify"));
const { width, height, pixels } = await r.render({ size: 256 }); // RGBA
const src = await r.dataUri({ size: 256 });                      // PNG data URI
```

Renders are memoized per size. Small outputs run the field pipeline at a
reduced internal resolution (smallest power of two ≥ 2× the output; floor
256, or 128 for outputs ≤ 32px) — 15–70× faster than the full pipeline
with measured RMSE within ±0.4 of exact at display sizes. Pass
`{ exact: true }` to force the full 1024² pipeline (bit-identical to the
pre-small-N engine); sizes ≥ 512 always use it.

## Building recipes

The batch harness is `pipeline/build-recipes.mjs` (measure + report, then
`--adopt <maxRmse>`). For single-icon work and the full procedure, quality
bars, and debugging playbook, see the **glass-to-lut skill**
(`.claude/skills/glass-to-lut/SKILL.md`).

Requirements: macOS with Icon Composer, Node ≥ 18, Python 3 with numpy +
Pillow (set `PYTHON` to a venv). To extract `.icon` bundles from compiled
apps, see [decant](https://github.com/kylebshr/decant).

## Package layout

```
engine.mjs        generated by tools/build_engine.py — do not edit by hand;
                  regeneration is byte-stable (web-bundler patches are baked
                  into the generator)
index.mjs         public API: createLiquidRenderer, loadRecipe, recipeSlugs
recipes/          adopted per-icon recipes (pure data, keyed by bundle slug)
PROVENANCE.md     where the calibration data comes from
calibration/      universal measured data (body polynomial, body-light LUT,
                  refraction law) — embedded into the engine at build time
tools/
  build_engine.py   emit engine.mjs
  build_recipe.py   .icon + ground truth -> recipes/<id>.mjs (two-phase)
  render.mjs        render a recipe to PNG in Node
  score.py          RMSE against ground truth (+ side-by-side diff image)
```

## Note on icon artwork

Recipes generated from third-party `.icon` bundles reproduce those apps'
icon artwork. The tooling here is MIT-licensed (repo root LICENSE); the
*artwork* a recipe encodes remains the property of its owner. Ship recipes
for logos you have the right to use.
